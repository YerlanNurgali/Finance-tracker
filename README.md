# Finance Tracker

Веб-приложение и консольный трекер доходов и расходов на FastAPI и PostgreSQL. Production-хранилище — Neon PostgreSQL; строка подключения всегда берётся из `DATABASE_URL`.

## Возможности

- доходы и расходы с категориями;
- баланс, история, фильтры по периоду и статистика по категориям;
- редактирование и удаление операций, выбор даты и времени операции;
- собственные категории доходов и расходов (вкладка «Настройки»): создание, переименование и удаление с переносом операций в «Другое»; категорию с бюджетом удалить нельзя;
- CSV-экспорт;
- адаптивный PWA-интерфейс с офлайн-кэшем последнего загруженного состояния;
- локализация интерфейса на KZ / EN / RU с сохранением выбора между перезагрузками.
- современный dashboard с фильтрами истории, быстрым добавлением операций и аналитикой;
- светлая и тёмная темы с сохранением выбора и поддержкой prefers-reduced-motion.

## Структура

`database.py` содержит PostgreSQL-слой и безопасные транзакции, `storage.py` — адаптер консольного формата, `operations.py` и `finance.py` — доменную логику, `api.py` — HTTP API, а `frontend/` — PWA.

## Локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export DATABASE_URL='postgresql://user:password@host/dbname?sslmode=require'
export SECRET_KEY='длинная-случайная-строка'  # например: python3 -c "import secrets; print(secrets.token_hex(32))"
uvicorn api:app --reload
```

Откройте `http://127.0.0.1:8000`. Для консольного режима используйте `python3 main.py`.

Подключения к базе переиспользуются через пул (`psycopg2.pool.ThreadedConnectionPool`). Необязательные переменные: `DB_POOL_MIN` (по умолчанию 5 — столько простаивающих подключений пул держит открытыми между всплесками нагрузки), `DB_POOL_MAX` (10) и `DB_POOL_TIMEOUT` — сколько секунд ждать свободного подключения (10). Значения должны быть положительными, иначе приложение не запустится и сообщит, какая переменная задана неверно; если `DB_POOL_MIN` больше `DB_POOL_MAX`, используется `DB_POOL_MAX`. Каждое подключение открывается с `connect_timeout=10`.

## Импорт банковских CSV

Кнопка «Импорт CSV» рядом с экспортом открывает мастер: файл → столбцы → проверка → результат. Поддерживаются UTF-8 и UTF-8 с BOM, разделители `,` и `;`, форматы дат `DD.MM.YYYY`, `DD/MM/YYYY`, `MM/DD/YYYY`, `DD-MM-YYYY`, `YYYY-MM-DD` (с временем или без) и три способа обозначить доход и расход: знак суммы, отдельный столбец типа или два столбца прихода и расхода. Ограничения: 1 МБ, 5000 строк, 50 столбцов. Операции в валюте, отличной от валюты профиля, не импортируются.

Файл не хранится на сервере: `POST /import/csv/preview` и `POST /import/csv/commit` принимают его телом `text/csv`, а настройки — параметрами запроса. Повторный импорт не создаёт дубликатов: у каждой строки выписки есть отпечаток `import_hash`, уникальный для пользователя. Если указать столбец «Номер операции в банке», отпечаток строится по нему; иначе — по дате, типу, сумме и описанию (описание не сохраняется). Одинаковые строки внутри файла различаются номером повтора, поэтому две настоящие одинаковые покупки не сливаются в одну. Лимит запросов импорта считается по пользователю.

Тесты на настоящем PostgreSQL (миграция, параллельный импорт, откат) работают только в локальной песочнице (см. «Тесты» ниже): тесты пересоздают таблицы. Разбор CSV — в `bank_import.py`; там же `BANK_PRESETS` для будущих форматов конкретных банков.

## Тесты

```bash
python3 -m pytest -q
```

Обычные тесты работают с подменёнными подключениями (`database.get_connection` и `psycopg2.connect` заменяются фейками) и к базе не подключаются. Для запуска самого сервера нужна установленная зависимость `psycopg2-binary` и доступный `DATABASE_URL`. Защита тестов описана ниже. Она **не абсолютна**: это набор проверок, который ловит случайные подключения и очевидные обходы.

### Запрещённые команды

Без отдельного разрешения не выполняйте:

- `pytest migrate_to_v2.py`, `pytest migrate_sqlite_to_neon.py` и любой другой файл вне `tests/`, переданный pytest по пути (в том числе `pytest main.py`, `pytest database.py`, `pytest . --doctest-modules`);
- `pytest --noconftest`, `pytest --confcutdir=…`, `pytest -p no:…` и другие запуски, при которых `tests/conftest.py` может не загрузиться;
- `python3 migrate_to_v2.py` и другие миграции — они рассчитаны на production и подключаются к базе из `.env`;
- `python3 tests/pg_sandbox.py init` с URL, который указывает не на ваш локальный одноразовый сервер.

**Миграции нельзя передавать pytest (К-1: для `migrate_to_v2.py` закрыт структурой файла и дополнительным guard, в целом не решён).** pytest импортирует явно переданный файл, даже если имя не подходит под `python_files`, а `collect_ignore` и `--ignore` на такой файл не действуют. При этом `tests/conftest.py` загружается только для путей внутри `tests/`, поэтому запуск `pytest <файл вне tests/>` идёт **без защиты тестов**. `testpaths = tests` в `pytest.ini` защищает только запуск без аргументов (по чтению исходников pytest 8.4.2 в `.venv`, запуском не проверено).

Как устроен `migrate_to_v2.py` сейчас:

- Весь исполняемый код миграции находится внутри `main()`: `import psycopg2`, `load_dotenv()` (загрузка `.env`), чтение `DATABASE_URL`, подключение к базе, SQL (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE operations`, `INSERT`, `UPDATE operations`), `COMMIT`. На верхнем уровне остались только импорты `os` и `sys`, guard и определение `main()`.
- `main()` вызывается только строкой `if __name__ == "__main__": main()` в конце файла, то есть при прямом запуске `python3 migrate_to_v2.py`. Импорт модуля `main()` не вызывает.
- В самом начале (сразу после `import os`/`import sys`, до `main()`) стоит дополнительный guard: если в `sys.modules` уже есть `pytest` или `_pytest`, файл завершается с `RuntimeError`. Это вторая линия защиты, а **не универсальная гарантия**: она не действует, когда pytest не загружен.

**Прямой запуск `python3 migrate_to_v2.py` выполняет миграцию и способен изменить production-базу (подключение берётся из `.env`). Он запрещён без отдельного разрешения.**

Структура файла и guard проверены чтением текста и статическими проверками в `tests/test_safety_net.py` (они входят в полный набор тестов, который проходит). Как именно pytest покажет ошибку guard при явной передаче файла (ошибка сбора, трассировка при `-p`), отдельно не проверялось. Сохранение SQL и порядка шагов при переносе в `main()` сверено с прежним текстом только вручную; сама миграция не запускалась.

Что это **не** закрывает:

- любой запуск без pytest: прямой запуск файла (см. выше), другой интерпретатор или инструмент, который выполнит `main()` напрямую;
- другие корневые скрипты. По беглому чтению (Этап 0.12, только текст, часть файлов прочитана не целиком) `main.py` и `migrate_sqlite_to_neon.py` при импорте не подключаются к базе, их работа под `__main__`; но `database.py`, который они импортируют, загружает `.env` при импорте, и ранней защиты от pytest в них нет. Полный перечень корневых файлов получить не удалось, поэтому `pytest <любой корневой файл>` остаётся запрещённым;
- гарантию, что pytest всегда оставляет `pytest`/`_pytest` в `sys.modules` (по чтению исходников — да, запуском не проверено).

Корневой `conftest.py`, который отказывался бы собирать `.py` вне `tests/`, не создавался: это требует отдельного решения. Он не остановил бы `-p`, `PYTEST_PLUGINS`, `--noconftest` и `--confcutdir`/`-c` внутри проекта (по исходникам pytest).

### Защита тестов от настоящей базы

Правила в `tests/db_safety.py`, подключение — в `tests/conftest.py`.

Ниже описано, что делает код по его тексту. Работа защиты подтверждена прогоном `tests/test_safety_net.py` (в составе полного набора: `1097 passed`) и PostgreSQL-тестами на локальной песочнице (63 теста прошли). Гарантии ограничены перечисленным ниже: туннели, код вне `psycopg2` и подмена окружения вне процесса исполнением не проверялись.

Что обеспечивает код по его тексту (для подключений через `psycopg2.connect`, в том числе из пула):

- **Окружение.** До импорта приложения:
  - выставляется `PYTHON_DOTENV_DISABLED=1`. Загрузит ли после этого python-dotenv `.env`, зависит от его версии (в установленной, судя по её исходникам, не загрузит; см. «зависит от поведения библиотек»);
  - из `os.environ` удаляются все переменные `PG*`, включая пустые;
  - `DATABASE_URL` заменяется заглушкой на закрытый порт. Это держит и без отключения `.env`: python-dotenv по умолчанию не перезаписывает уже заданные переменные. Другие значения из `.env` (в том числе `SECRET_KEY`) при этом могли бы попасть в окружение.
- **Подлинность модулей.** `conftest.py` проверяет, что `db_safety` загружен из `tests/db_safety.py`, а `database` и `api` — из корня проекта. `psycopg2` (и его C-модуль) и `python-dotenv` должны быть загружены из `site-packages`/`dist-packages`, а не из файла с тем же именем в `tests/` или раньше в `sys.path`. Иначе запуск останавливается.
- **Перехват подключения.** Проверка стоит на весь процесс на обоих именах одной и той же функции: `psycopg2._connect` (её вызывает `psycopg2.connect` с итоговым DSN) и `psycopg2._psycopg._connect` (собственное имя модуля-расширения). Поэтому подмена `psycopg2.connect` на функцию, вызывающую второе имя напрямую, тоже отклоняется. Подключение отклоняется **до** вызова драйвера, если это не подключение к проверенной песочнице из теста PostgreSQL.
  - Допускаются только литеральный loopback-адрес (`127.0.0.1` или `::1`, не `localhost`), порт, база и роль песочницы, заданные опции `-c` и короткий список безвредных параметров.
  - Любой другой параметр (`service`, `hostaddr`, `passfile`, `sslcert`, `target_session_attrs`…) отклоняется.
  - Принимается только та форма вызова, которую использует `psycopg2.connect`: ровно один DSN и ключи `connection_factory`, `async`/`async_`. Лишние позиционные аргументы и неизвестные ключи отклоняются, драйвер их не получает.
  - Собственный `connection_factory` отклоняется, в том числе класс с нестандартным метаклассом.
  - Перед каждым подключением обёртка сама первым делом выполняет проверку целостности (см. ниже): при любой найденной проблеме подключение отклоняется. Нужные встроенные имена (`len`, `set`, `str`, `type`, `Exception`) и классы ошибок обёртка использует через ссылки, привязанные при установке.
- **Окно.**
  - Проверяется при каждом подключении: окно на удалённый хост или с чужими опциями не принимается.
  - Открытое окно должно совпадать с одним из трёх законных способов открытия:
    - временное окно работающего `verify_sandbox`;
    - окно последней конфигурации, принятой `verify_sandbox` (`activate`, фикстура `pg_gate`);
    - `open_gate` вне pytest (`pg_sandbox.py init`).

    Окно, выставленное вручную, отклоняется и видно в проверке целостности.
  - Принятые конфигурации записываются в журнал проверок, из которого ничего не удаляется. Под pytest `open_gate` отказывает.
- **Нормализация DSN.** В DSN, который уходит в libpq, дописывается `hostaddr=<тот же адрес>`, а строка пересобирается функцией `make_dsn` из psycopg2. Код проверяет, что после нормализации разобранные параметры совпадают с проверенными, а добавился только `hostaddr`.
- **Ошибки проверки.** Любое неожиданное исключение внутри проверки тоже даёт отказ и записывается в журнал (без DSN).
- **Журнал отказов.**
  - Каждый отказ записывается вместе с потоком и учитывается счётчиком.
  - Отказ во время теста или его фикстур проваливает этот тест, даже если приложение проглотило ошибку. Отказ при сборе останавливает сессию. Отказ между тестами проваливает следующий тест.
  - В конце сессии (`pytest_sessionfinish`, `pytest_unconfigure`) любой отказ или подмена делают результат неуспешным, при этом собственный ненулевой код pytest сохраняется.
  - При выходе из интерпретатора выполняется последняя проверка (`_at_exit`). `os._exit(3)` вызывается, **только** если сессия на этот момент считает себя успешной (статус `OK` или `NO_TESTS_COLLECTED`, либо статуса нет вовсе) и при этом найден отказ или подмена. Так бывает, если какой-то хук вернул статус «успех» или отказ случился после последнего хука. Если статус уже неуспешный, `os._exit` не вызывается и код pytest остаётся прежним: сообщение печатается только при позднем отказе (после последнего хука), в остальных случаях проверка молча завершается, потому что хуки уже всё сообщили.
  - Ожидаемые отказы разрешены только в теле теста с маркером `expect_blocked` в `tests/test_safety_net.py` (блок `expected_refusals(n)`). Разрешение привязано к id этого теста и к фазе `call`, а снимаются только отказы того же потока. Они переносятся в отдельный журнал.
  - Если проверка песочницы (`pg_sandbox`) не прошла, отказы, записанные к этому моменту, переносятся в журнал отчитанных и добавляются к тексту ошибки. Иначе они всплыли бы позже как «отказ вне теста» в другом тесте. Это не зависит от порядка, в котором pytest готовит фикстуры; берутся все накопленные отказы, не только отказы проверки.
- **Целостность.** Состояние (окно, проверенная песочница, журналы, счётчик) хранится в замыканиях функций `db_safety`, а не в словаре модуля. Проверка целостности сравнивает с эталоном, снятым при импорте и хранящимся в неизменяемых кортежах:
  - все глобальные имена модуля и **появление новых**: имя вроде `len`, `set`, `type`, `isinstance` или `Exception` в словаре модуля затенило бы встроенное в каждой его функции. Новое служебное имя `__*` считается подменой, только если так называется встроенный объект (`__import__`); значения служебных имён в эталон не входят. Это проверяется первым шагом, на ссылках, привязанных при импорте. Там же сверяется, что объект `__builtins__` модуля не заменён и что **каждое встроенное имя, на которое ссылается код `db_safety`** (`len`, `isinstance`, `sorted`, `Exception`…; список берётся из объектов кода при импорте), по-прежнему тот же объект в словаре встроенных. Не сверяются остальные встроенные имена и встроенное, достигнутое иначе, чем по имени в тексте кода (например, `getattr` с вычисляемым именем);
  - код, значения по умолчанию и ячейки замыкания функций модуля и функций в их ячейках;
  - перехват на `psycopg2`: `connect`, `_connect`, обёртку и её ячейки, `psycopg2._psycopg._connect` (должна быть той же обёрткой), `extensions.connection`, место загрузки пакета;
  - согласованность окна и журнала проверок.

  У функции проверки нет режима по умолчанию: каждый вызов явно указывает, допускается ли подменённый `psycopg2.connect`. `conftest.py` держит ссылку на функцию, полученную при импорте. Проверка выполняется:
  - при загрузке `conftest.py` и после импорта приложения;
  - в конце сбора;
  - перед каждым тестом и непосредственно перед его телом;
  - перед проверкой песочницы и перед открытием окна;
  - после теста и в конце сессии;
  - внутри обёртки при каждом подключении.

  Что происходит при найденной проблеме, зависит от места. Проверки при загрузке `conftest.py` прерывают импорт ошибкой. Проверки в конце сбора, перед тестом, перед его телом, до и после сброса состояния и в фикстурах песочницы останавливают сессию (`pytest.exit`). В конце сессии (`pytest_sessionfinish`, `pytest_unconfigure`) и при выходе (`_at_exit`) проблема не останавливает работу, а делает результат неуспешным. Проверка внутри обёртки только отклоняет это подключение и записывает отказ. Подмена `psycopg2.connect` допускается только на время теста — код не отличает `monkeypatch` от простого присваивания.
- **Восстановление состояния.** Снимок делается один раз, при загрузке `conftest.py`, до тестовых модулей. До и после каждого теста восстанавливаются:
  - всё окружение (`os.environ`), кроме `PYTEST_*`;
  - все глобальные имена модулей `database` и `api` (кроме пула и кэша шрифтов) и верхний уровень их обычных словарей, списков и множеств;
  - у приложения: `dependency_overrides`, `exception_handlers`, `user_middleware`, маршруты, хуки `on_startup`/`on_shutdown`, сам объект `app.state` и его содержимое, кэш `openapi_schema`.

  Пул подключений закрывается, окно — тоже. Если само восстановление выбросило исключение, сессия останавливается (`pytest.exit`). Если оно отработало, но вернуть что-то не удалось (пул не закрылся, `DATABASE_URL` или `PG*` не вернулись) или окно было найдено открытым и закрыто сбросом, **падает этот тест**, а сессия продолжается: следующий тест повторяет сброс и падает снова, пока остаток не исчезнет. Целостность проверяется и до сброса (иначе сброс закрыл бы вручную открытое окно раньше проверки), и после него. Что до сброса не было ложных срабатываний, выведено из порядка фикстур по тексту, запуском не проверено.
- **Подпроцессы.** Окружение собирается только по белому списку (`safe_subprocess_env`): `PATH`, локаль, временные каталоги, заглушка `DATABASE_URL`, отключённый `.env`.
  - Через `extra` нельзя передать `PG*`, `FT_TEST_*`, `PYTHON*`, `LD_*`, `DYLD_*`, `DATABASE*`, `LC_*` и значения, похожие на параметры подключения.
  - `tests/subprocess_guard/sitecustomize.py` запрещает в дочернем процессе подключения через `psycopg2` и импорт других драйверов PostgreSQL.
  - Если поставить запрет не удалось или `psycopg2` загружен не из установленного пакета, процесс завершается через `os._exit` до запуска своего кода.

Что зависит от поведения библиотек (выведено из документации и чтения исходников, кодом не доказано):

- **libpq:** явный `hostaddr` в строке подключения сильнее `PGHOSTADDR` и параметров из файла сервисов (`PGSERVICE`), поэтому адрес, заданный в обход `os.environ`, подключение не перенаправит. Это документированное поведение libpq, а не свойство кода.
- **python-dotenv:** `PYTHON_DOTENV_DISABLED=1` отключает загрузку `.env` (по чтению исходников установленной версии 1.2.1; более старые версии переменную не знают). Если это не так, остаётся лишь то, что `DATABASE_URL` уже задан и не перезаписывается.
- **psycopg2:** `psycopg2.connect` вызывает `_connect(dsn, connection_factory=…, [async_=…])`, а итоговую строку для libpq собирает сама защита (`_harden_dsn`): добавляет `hostaddr`, все значения берёт в одинарные кавычки и экранирует `\` и `'` (так не-ASCII пароль не разрезается: `make_dsn` psycopg2 кавычит значение только при Unicode-пробеле). Результат разбирается `parse_dsn` и сравнивается с исходным разбором плюс `hostaddr`; DSN с уже заданным `hostaddr` отклоняется. Ограничение: `psycopg2.connect` с дополнительными параметрами (так подключается пул приложения) вызывает `make_dsn` до защиты, и с таким паролем подключение не открывается вовсе, поэтому для роли песочницы нужен пароль только из ASCII. `psycopg2._connect` и `psycopg2._psycopg._connect` при установке — один и тот же объект (иначе установка защиты завершается ошибкой); что остальной код `psycopg2` не вызывает второе имя иначе, чем через первое, — предположение о библиотеке: такой вызов был бы отклонён, а не пропущен. Установка защиты (запись атрибута в модуль-расширение) проходит в прогонах тестов; при ошибке установка завершается ошибкой.
- **pytest:** итоговый код процесса — это `session.exitstatus` после `pytest_unconfigure`; `PYTEST_CURRENT_TEST` во время теста имеет вид `"<id> (call)"`; автоматические фикстуры применяются к `unittest.TestCase`.
- **CPython:** запись в `__closure__`, `__code__` и `__defaults__` обнаруживается сравнением со снимком; обработчики `atexit` выполняются в обратном порядке регистрации.
- **Starlette/FastAPI:** `app.state`, `openapi_schema`, `exception_handlers` и списки маршрутизатора — обычные атрибуты, которые можно вернуть на место.
- **PostgreSQL:** SQL проверок песочницы и права по умолчанию в вашей версии (проверено на PostgreSQL 17.11).

Подтверждено прогонами: `tests/test_safety_net.py` и полный набор (`1097 passed`, 12 предупреждений). Исполнением не проверялись остаточные риски, перечисленные ниже (туннели, код вне `psycopg2`, подмена окружения вне процесса), и допущения о других версиях библиотек и PostgreSQL.

Чего код **не** гарантирует (известные обходы и остаточные риски):

- Подключение в обход обоих имён `_connect`: прямое создание `psycopg2.extensions.connection` или классов из `psycopg2.extras`, другой драйвер, нативный код, запуск `psql`, HTTP-API базы. Такие случаи ищут только статические проверки.
- **Прерывание во время установки защиты.** Ошибка записи в C-модуль (`Exception`) откатывает `psycopg2._connect`, установка завершается ошибкой, обёртка не регистрируется. Регистрация стоит последней, поэтому состояние «зарегистрирована, но не установлена» невозможно. Исключение, не являющееся `Exception` (`KeyboardInterrupt`, `SystemExit`), между двумя записями намеренно не перехватывается: системные исключения не подавляются и не заменяются. Тогда `psycopg2._connect` остаётся с обёрткой, `psycopg2._psycopg._connect` — без неё, и обёртка не зарегистрирована. Проверка целостности сообщает «the guard is not installed» (любой `psycopg2.connect` отклоняется, а загрузка `conftest.py` прерывается ошибкой), но прямой вызов `psycopg2._psycopg._connect` в этом окне не отклонялся бы. Прерывание обычно завершает процесс. Откат `psycopg2._connect = real_connect` тоже не защищён от сбоя. Это выведено из текста и не проверено.
- **Защиту от намеренного вмешательства внутри процесса.** Замыкания и снимки делают подмену заметной, но не невозможной. Не обнаруживается:
  - замена кода или эталонных данных самой функции проверки. Она входит в снимок защитной обёртки, но сверяет себя сама с собой, поэтому подменённый код просто не сообщит о подмене;
  - одновременная правка нескольких полей состояния через ячейки замыкания (например, окна вместе с журналом проверок);
  - изменение методов классов `Gate`, `SafetyError`, `BlockedConnection`;
  - обход объектов через `gc` и `ctypes`;
  - кратковременную подмену встроенного или глобального имени внутри одного теста, если её вернули назад до следующей проверки: целостность проверяется в определённые моменты (список выше), а не непрерывно, и проверка с использованием не атомарны (между ними может пройти время или чужой поток);
  - замену встроенного, которое код `db_safety` использует иначе, чем по имени в тексте (`getattr` с вычисляемым именем), и значений служебных имён модуля (`__name__`, `__spec__`…).

  Это запрещают только статические проверки.
- Переменные окружения, которые libpq читает сам, кроме адреса (например, `sslmode` или файл паролей), если их задать в обход `os.environ`.
- **Неполное восстановление глобального состояния.** Не восстанавливаются:
  - объекты глубже верхнего уровня контейнеров;
  - уже собранный `app.middleware_stack` (поэтому откат `user_middleware` после первого запроса ничего не меняет);
  - счётчики ограничителя запросов (тесты сбрасывают их сами);

  Настройки, которые фикстуры уровня модуля или класса делают один раз, откатываются перед каждым тестом — такие тесты могут падать. Для `middleware_stack` и счётчиков нужны знания о жизненном цикле Starlette и slowapi — это отдельная задача.

  Список восстанавливаемых атрибутов приложения (`app`) намеренно не расширялся «на всякий случай»: остальные его атрибуты (`debug`, `router.default`, `router.lifespan_context`, `extra`…) не восстанавливаются, потому что их устройство в установленных версиях Starlette/FastAPI не проверено. Если какой-то из перечисленных атрибутов в другой версии Starlette окажется не словарём и не списком, `_app_containers` пропустит его молча.

Тест вызывает приватную функцию `conftest.py`. `test_every_test_starts_from_the_original_application_state` проверяет лишь исходное состояние и сам по себе почти ничего не доказывает; ещё один независимый от порядка тест проверяет примитивы снимка и восстановления на реальных модулях. Ни один из них не запускался.

Обработчик, зарегистрированный позже и сам вызывающий `os._exit`, выполнится раньше нашего. При вызове `pytest.main()` внутри другой программы её завершение может быть принудительным. Поведение в воркерах xdist не проверено.
- Подлинность `psycopg2`, если подменный модуль положен прямо в каталог с именем `site-packages`.

### Песочница PostgreSQL

Тесты `*_postgres.py` (и любой тест, который использует фикстуры `pg_database_url`/`pg_gate`) рассчитаны **только** на отдельную изолированную одноразовую базу на вашем локальном сервере. Лучше отдельный локальный кластер только для тестов. Ни production, ни общий, ни удалённый сервер для этого не годятся. Имя базы, loopback-адрес или токен по отдельности ничего не доказывают, поэтому проверяется всё сразу, в сеансе только на чтение и до первого изменяющего запроса:

- URL на `127.0.0.1` или `[::1]` (не `localhost`: он зависит от `/etc/hosts`) с явным портом, база и роль `ft_test…`, без параметров в URL;
- сервер сообщает ту же базу и роль, loopback-адрес и тот же порт, что в URL, и не является репликой;
- у роли нет особых атрибутов и членства в каких-либо ролях (в том числе `pg_read_all_data`, `pg_write_all_data`, `pg_read_server_files`, `pg_monitor`);
- роль не владеет ни одной базой, владеет схемой `ft_test` и вне неё не владеет ничем — ни схемами, ни таблицами, ни последовательностями, ни функциями, ни типами, ни large objects;
- у роли нет `CREATE` и `TEMP` на базу и нет права подключаться к **другим** базам сервера;
- вне `ft_test` и системных схем у роли нет прав:
  - на схемы (`USAGE`, `CREATE`);
  - на таблицы и отдельные столбцы;
  - на последовательности;
  - на выполнение функций;
- у роли нет права выполнять опасные встроенные функции: чтение файлов сервера, `lo_import`/`lo_export`, перезагрузку конфигурации и т. п.;
- в базе нет расширений, кроме `plpgsql` (значит, нет `dblink` и `postgres_fdw`), нет foreign-data wrappers, foreign servers и user mappings;
- таблица-метка `ft_test.ft_test_sandbox_marker` содержит ровно одну строку с именем этой базы и токеном из `FT_TEST_POSTGRES_TOKEN`.

Окно для подключений открывается только для конфигурации, прошедшей эту проверку. Удалённая песочница не поддерживается. SQL этих проверок выполнен на локальной песочнице PostgreSQL 17.11 (проверка сервера прошла); запрос по последовательностям вызывает `has_sequence_privilege` только для объектов-последовательностей (через `CASE`), иначе PostgreSQL отвечает `WrongObjectType`. Если какое-то право в вашей версии PostgreSQL по умолчанию выдано PUBLIC, проверка откажет (это безопасная сторона), и права придётся отозвать.

Чего эти проверки **не** доказывают:

- **Что сервер физически на этой машине.** Адрес и порт со стороны сервера (`inet_server_addr()`, `inet_server_port()`) отсекают только явно чужое. Туннель SSH (`ssh -L 5432:localhost:5432 db-host`), VPN или `kubectl port-forward` с одинаковым портом на обоих концах выглядят как локальный сервер. За то, что URL указывает на **ваш** локальный сервер, отвечаете вы. И наоборот: локальный Docker с пробросом порта будет отклонён — сервер видит адрес контейнера.
- **Полную изоляцию.** Проверки видят только каталог базы песочницы: права в других базах, на файлы сервера и в операционной системе им не видны.
- **`search_path=ft_test` — не граница безопасности:** SQL с явной схемой дойдёт до любой схемы, к которой у роли есть доступ. Защищают права отдельной роли.
- **Квалификация `DROP`/`DELETE`/`UPDATE`/`ALTER` схемой `ft_test`** в тестах проверяется статически, но это соглашение, а не запрет.

```bash
python3 tests/pg_sandbox.py print-setup-sql      # SQL для администратора ЛОКАЛЬНОГО сервера: роль ft_test_runner (без пароля), база ft_test_sandbox, схема ft_test
# в psql под суперпользователем: \password ft_test_runner — задайте свой пароль
export FT_TEST_POSTGRES_URL='postgresql://ft_test_runner:<ваш пароль>@127.0.0.1:<порт>/ft_test_sandbox'
python3 tests/pg_sandbox.py init                 # проверяет назначение базы и создаёт метку; токен не печатается
# в psql, подключившись к ft_test_sandbox: SELECT token FROM ft_test.ft_test_sandbox_marker;
export FT_TEST_POSTGRES_TOKEN='<этот токен>'
python3 -m pytest -q
```

`print-setup-sql` отзывает `CONNECT` у PUBLIC для баз `postgres` и `template1` — это затрагивает все роли сервера, поэтому для тестов лучше отдельный локальный кластер. Для других баз, которые есть на сервере, отзыв нужно повторить.

Если переменная задана, но песочница не прошла проверку, тесты PostgreSQL завершаются **ошибкой**, а не пропуском, и в базе ничего не меняется. База песочницы не должна содержать чужих таблиц с именами приложения вне схемы `ft_test` (миграция в `database.py` ищет колонки в `information_schema` без фильтра по схеме).

## API

- `GET /operations?period=all|today|week|month`
- `POST /operations` с JSON `{date, operation_type, amount, category}`
- `PUT /operations/{id}` и `DELETE /operations/{id}`
- `GET /categories`, `POST /categories`, `PUT /categories/{id}`, `DELETE /categories/{id}?move_to=` — собственные категории пользователя (контракт — в `API_DOCUMENTATION.md`)
- `GET /balance`, `GET /statistics`, `GET /export/csv`, `GET /export/excel`, `GET /export/pdf`, `GET /health`

Расходы требуют категорию, суммы должны быть положительными и помещаться в `NUMERIC(14, 2)`: от 0,01 до 999 999 999 999,99 после округления до копеек. Ошибки валидации возвращаются с HTTP 422, неизвестная операция — с HTTP 404.

Дату и время операции можно выбрать при добавлении и редактировании (по умолчанию — текущие). Сервер проверяет новую дату: поддерживаются `DD.MM.YYYY, HH:MM:SS` (формат интерфейса и импорта), `DD.MM.YYYY, HH:MM`, `DD.MM.YYYY HH:MM`, `YYYY-MM-DDTHH:MM`, `YYYY-MM-DD` и просто `DD.MM.YYYY` (сохраняется как полночь). Дата не может быть раньше 01.01.2000 и позже, чем через 31 день от часов сервера; нечитаемая дата отклоняется с HTTP 422 и никогда не заменяется текущей. Уже сохранённые операции не переписываются. Операции с будущей датой сразу входят в баланс; расход за прошлый месяц учитывается в бюджете своего месяца без предупреждения. История идёт в порядке добавления, а не по дате. При редактировании операции с нераспознаваемой датой интерфейс просит выбрать дату заново. Проверки дат — в `tests/test_v2_core.py` и `tests/test_integration.py` (входят в полный набор, который проходит).

## Экспорт в Excel и PDF

Excel строится через `openpyxl`, PDF — через `reportlab` (обе зависимости в `requirements.txt`). Стандартные шрифты PDF не содержат кириллицы, поэтому в PDF встраивается TrueType-шрифт с русскими и казахскими буквами. Его путь можно задать переменной `PDF_FONT_PATH` (и `PDF_BOLD_FONT_PATH` для заголовков); иначе используется первый найденный из DejaVu Sans, Noto Sans, Liberation Sans (Linux), Arial Unicode (macOS) или Arial (Windows). Без жирного начертания заголовки печатаются обычным. Если подходящего шрифта нет, `GET /export/pdf` отвечает 503, а в лог пишется подсказка. Знак `₸` выводится, только если он есть в шрифте (в Arial Unicode его нет), иначе — `KZT`; символы, которых нет в шрифте, заменяются на `?`. Длинные значения переносятся внутри колонки, заголовок таблицы повторяется на каждой странице.

## Предупреждения о бюджетах

Бюджет считается по **календарному месяцу** (по дате операции), а не по последним 30 дням. Предупреждение приходит, когда уровень **растёт**: 80 % — предупреждение, ровно 100 % — лимит исчерпан, больше 100 % — превышение. Достигнутый уровень хранится для каждого бюджета и месяца в таблице `budget_alert_state`, поэтому повторный расход на том же уровне, обновление страницы и повторный импорт того же CSV ничего не показывают; когда расходы падают (операцию изменили или удалили, лимит подняли), уровень снижается молча, и новое пересечение порога снова предупреждает. Пересчёт идёт после добавления, изменения и удаления операции (с учётом прежней и новой категории и даты), после создания и изменения бюджета (без предупреждения) и после CSV-импорта (только по реально сохранённым строкам). Предупреждения только за текущий месяц; из-за разницы часов сервера и пользователя на стыке месяцев текущими считаются оба.

В настройках аккаунта есть переключатель предупреждений в приложении (`budget_alerts_inapp`, по умолчанию включён у всех); поле `budget_alerts_push` тоже хранится, но push-уведомления пока не отправляются (нужны ключи VAPID и новая зависимость). Миграция при старте идемпотентна: `ALTER TABLE user_settings ADD COLUMN IF NOT EXISTS …` и `CREATE TABLE IF NOT EXISTS budget_alert_state`; существующие данные не меняются.

Тесты: логика уровней и API — `tests/test_budget_alerts.py`; SQL, миграция, параллельные запросы и весь путь через API на настоящем PostgreSQL — `tests/test_budget_alerts_postgres.py` (только в локальной песочнице, см. «Тесты»). Защита тестов от настоящей базы описана там же.

## Neon и Render

Создание таблицы выполняется при старте приложения через `CREATE TABLE IF NOT EXISTS`; существующие записи не удаляются. На Render можно использовать включённый `render.yaml`: добавьте секретные `DATABASE_URL` и `SECRET_KEY` в Environment и не коммитьте `.env`. `SECRET_KEY` подписывает токены входа: без него каждый запуск создаёт случайный ключ, и все пользователи выходят из системы после перезапуска — при старте в лог пишется предупреждение. Лимиты `/auth/login` и `/auth/register` считаются по IP клиента. В `render.yaml` объявлены `SECRET_KEY` (значение задаётся в панели Render, не в файле) и `FORWARDED_ALLOW_IPS="*"`: uvicorn доверяет заголовку `X-Forwarded-For` от прокси Render и видит реальный IP клиента, иначе все клиенты делили бы один лимит. Это безопасно, только пока сервис доступен лишь через прокси Render (не из других сервисов во внутренней сети: они могли бы подставить чужой IP). Push из проекта не выполняется автоматически.

Service worker имеет версию кэша `v11`, удаляет старые версии при активации и использует сеть с fallback на кэш, поэтому обновления JavaScript не застревают в старом кэше.

Frontend использует CSS variables для единого design system, поддерживает фильтрацию истории без дополнительного запроса и позволяет переключать светлую/тёмную тему без перезагрузки. Версия service worker обновляется при изменении frontend-ресурсов.

Интерфейс поддерживает казахский (`kk`), английский (`en`) и русский (`ru`). Выбранный язык сохраняется в браузере. API и база данных продолжают использовать существующие canonical Russian values (`Доход`, `Расход`, `Зарплата`, `Еда`, `Транспорт`); перевод выполняется только на presentation layer frontend.
